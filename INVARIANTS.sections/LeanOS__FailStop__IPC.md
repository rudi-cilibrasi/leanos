# Messages, sealed transfers, and scheduler replies keep the kernel consistent

These theorems show that accepted returns to user programs, message sends and receives, and sealed capability transfers each preserve the global runtime invariant, and that every scheduler reply exactly matches the scheduler's own decision.

- `gate_userReturn_accepted_preserves_runtimeWellFormed` — An accepted outgoing return through the gate preserves the invariant, changes nothing at all, and reports exactly the typed success; the invariant itself forces the armed policy to match the live mapping plan.
- `gate_userReturn_preserves_runtimeWellFormed` — The complete outgoing-return operation preserves the invariant: success is a no-op, and every malformed or unselected proposal latches the execution halt and the snapshot-bank halt together, so the two fail-stop flags can never disagree after a rejection.
- `gate_restart_preserves_runtimeWellFormed` — Restart is the do-nothing running operation and so preserves the full invariant while touching no subsystem state.
- `gate_syscall_access_accepted_preserves_runtimeWellFormed` — An accepted access-check-only system call leaves virtual memory untouched, reselects return policy only through the live-plan check, preserves the entire invariant, and reports the exact typed success.
- `gate_sealed_receive_preserves_runtimeWellFormed` — The guarded rejection of a receive aimed at a sealed-transfer mailbox is a genuine no-op that preserves the entire invariant; the message is never consumed and patched up afterwards.
- `endpointSend_capabilities_unchanged` — Bookkeeping: sending a message through a channel never changes the permission registry.
- `endpointSend_preserves_occupied_mailbox` — Sending a message never overwrites a mailbox that already holds one: an occupied mailbox keeps its exact contents.
- `endpointSend_preserves_live_senders` — After any send, every message sitting in any mailbox still names a live sender.
- `endpointReceive_capabilities_unchanged` — Bookkeeping: receiving a message never changes the permission registry.
- `endpointReceive_preserves_other_mailbox` — A stepping-stone fact used by later theorems: receiving from one endpoint never disturbs a message waiting in any other endpoint's mailbox.
- `endpointReceive_mailbox_provenance` — A stepping-stone fact used by later theorems: any message found in a mailbox after a receive was already there before it, so a receive can only remove messages, never invent them.
- `gate_ipc_send_accepted_preserves_runtimeWellFormed` — Whenever a program's message send succeeds, the kernel updates every duplicated view of the endpoint in one step, leaves all pending sealed transfers exactly as they were, keeps its whole bookkeeping consistent, and reports exactly the "sent" reply.
- `gate_ipc_receive_accepted_preserves_runtimeWellFormed` — A successful receive consumes exactly the one chosen mailbox message, leaves every sealed attachment at every other endpoint intact, keeps the whole kernel consistent, and reports exactly who sent the message and the words it carried.
- `gate_transferOffer_accepted_preserves_transferWellFormed` — When a sealed capability hand-off offer is accepted, the transfer machinery's own records stay internally consistent and the gate reports exactly that acceptance.
- `gate_transferOffer_accepted_preserves_runtimeWellFormed` — An accepted sealed hand-off offer never removes any existing authority, so publishing it keeps every part of the kernel consistent while the pending gift and its notification message are recorded together as one atomic transfer state.
- `gate_transferAccept_delivered_preserves_capabilityWellFormed` — When a sealed hand-off is collected, the kernel's authoritative permission records stay consistent and the reply names the exact envelope and freshly installed generation word; this is the permission-store slice of the stronger whole-kernel theorem below.
- `gate_transferAccept_delivered_preserves_transferWellFormed` — The entire sealed-transfer record set, not just the permission store inside it, survives every completed collection of a hand-off, and the reply stays paired with the exact state and generation word that produced it.
- `installTransfers_preserves_runtimeWellFormed` — Publishing a transfer's outcome to the rest of the kernel is safe whenever it keeps the roster of live programs and objects, never removes authority anyone already held, and adds no message that was not already waiting; this is the shared boundary the collection step relies on.
- `gate_transferAccept_delivered_preserves_runtimeWellFormed` — Collecting a sealed hand-off removes the notification message, marks the offer finished, and installs the new permission into the receiver's verified-empty slot, all in one step that keeps the whole kernel consistent.
- `gate_rejected_mode_preserves_runtimeWellFormed` — When the kernel is busy handling an interrupt or already halted, every request is turned away without touching anything, so all of its bookkeeping stays consistent.
- `gate_scheduleAdd_accepted_sound` — When the scheduler accepts a new program into the ready queue, the public reply, the recorded scheduler state, and that state's internal consistency all match exactly what the scheduler itself produced.
- `gate_scheduleNext_accepted_sound` — The only way the raw "pick the next program" request can succeed is by selecting nobody, in which case the scheduler is left exactly as it was.
- `gate_scheduleRemove_accepted_sound` — Accepted removal from the ready queue also consumes the program's saved context and evicts its cached address translations, exactly as the resumable-aware cleanup routine specifies.
- `gate_scheduleYield_accepted_sound` — The raw "yield" request can never be reported as accepted, because it carries no saved context to switch away from; this theorem records that unreachable contract.
- `gate_scheduleTick_accepted_sound` — The raw timer-tick request likewise can never be reported as accepted; timer-driven switching belongs solely to the full save-select-restore operation.
- `gate_terminateCurrent_accepted_sound` — When the kernel terminates whichever program is currently running, it identifies that victim itself and retires the victim's address spaces, translations, mailboxes, transfers, and saved context in the same accepted step.
- `gate_terminateCurrent_accepted_cleans_deferred` — Terminating the current program performs exactly the same thorough cleanup as naming it explicitly; in particular no drainable saved context of the dead program can remain afterwards.
