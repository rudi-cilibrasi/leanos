# Suspending, resuming, and cleaning up programs

When the timer takes the processor away from a running program, the kernel must save that program's registers and return point as a snapshot, let the scheduler pick the next program, and restore that program's previously saved snapshot — all without ever letting one program's saved state leak into, replace, or select another's. These theorems guarantee that snapshots live in kernel-owned storage with exactly one entry per program, that the choice of what runs next comes only from the scheduler and never from any value a program controls, that every switch flushes the processor's address-translation cache, and that terminating a program erases everything it owned — its snapshot, its address spaces, its page mappings, and every handed-out permission to them — in one consistent step that can never damage what other programs own.

- `remove_rejected_unchanged` — Whenever removing a subject from the scheduler is refused, the kernel's state is left exactly as it was.
- `contextFor_owner` — Spelling out the definition: looking up a subject's saved snapshot only ever returns a snapshot that actually belongs to that subject.
- `contextFor_erase_self` — Spelling out the definition: after a subject's snapshot is erased from the kernel's bank, looking that subject up finds nothing.
- `contextFor_erase_other` — Erasing one subject's snapshot never changes what any other subject's lookup returns.
- `contextFor_save_consume` — Saving a snapshot installs exactly that kernel-owned entry: looking up the saved owner immediately afterwards finds precisely the snapshot just saved.
- `remove_accepted_exact` — A stepping-stone fact used by later theorems: an accepted removal is exactly the scheduler's own removal step plus the matching snapshot and translation updates, and it never leaves a running subject stranded with nobody waiting to run next.
- `remove_accepted_cleans_context_and_translation` — An accepted removal performs both required cleanups at once: the removed subject's saved snapshot is gone, and the recorded active address space matches whoever the scheduler now says is running.
- `remove_preserves_wellFormed` — Accepted removal keeps the kernel's entire combined bookkeeping sound — queue membership, the snapshot bank, and the translation record change together — while a removal that would strand the running subject with no possible successor is refused before anything is published.
- `wellFormed_set_halted` — Bookkeeping: flipping the permanent fail-stop latch on or off has no bearing on whether the state satisfies the soundness rules.
- `switch_accepted_flushes_translations` — Every successful save-select-restore switch performs the full address-cache flush, so the modeled translation cache comes out empty.
- `rejected_unchanged` — Whenever a switch is refused for any ordinary reason — anything short of a fatal entry — the kernel's state is left exactly as it was.
- `halted_reports_fatalEntry` — The only way a switch can leave the machine halted is by reporting the one distinguished fatal error; ordinary refusals can never set the permanent halt latch.
- `rejected_exposes_no_restore` — A refused switch never hands back any saved snapshot to run.
- `restored_context_is_scheduler_selected` — The snapshot a successful switch restores is exactly the bank entry named by the scheduler's own choice; neither the incoming registers nor any number a program supplies has any part in picking it.
- `restored_context_is_live_and_owned` — Whichever snapshot is restored belongs to a subject that is live and runnable after the scheduling step, running in the very address space recorded in its kernel-owned entry.
- `switch_preserves_scheduler_and_tlb` — A switch keeps both the scheduler's bookkeeping rules and the bounded translation-cache rules intact; the stronger snapshot-bank guarantees are stated by the separate ownership and separation theorems.
- `accepted_tick_is_select` — A stepping-stone fact used by later theorems: an accepted timer tick is exactly "move the running subject to the back of the queue, then select the new head."
- `accepted_tick_facts` — A stepping-stone fact: an accepted tick makes the selected subject the running one, leaves every ownership record untouched, and selects an address space that is exactly the selected subject's own.
- `accepted_tick_rotates_ready` — A stepping-stone fact: an accepted tick hands the turn to the subject at the head of the queue and moves the previously running subject to the back.
- `accepted_tick_has_restorable_destination` — In a sound state the timer can never select a subject whose kernel-owned snapshot is missing: the destination snapshot exists, passes every validity check, and names exactly the scheduler-selected subject and its address space.
- `switch_preserves_wellFormed` — Every save-select-restore switch preserves the complete combined bookkeeping, including the bank's size bound, the one-snapshot-per-owner rule, and the validity of every rewritten entry.
- `registers_cannot_select_restore` — An attacker who controls every general-purpose register of the interrupted program affects only what gets saved on its behalf; the registers can never influence which snapshot is chosen for restoration.
- `save_consume_preserves_other` — When one subject's snapshot is saved and another's is consumed in the same switch, every third subject's entry is left byte-for-byte unchanged.
- `retireOwnedAddressSpaces_preserves_retired_object` — Bookkeeping: retiring a subject's address spaces never brings an already-retired object back to life.
- `cleanupCapabilities_preserves_wellFormed` — Removing a subject and everything it owns only ever shrinks the permission records: every permission slot that survives still names the same live object of the same kind, and the append-only history of how permissions were derived is untouched.
- `cleanupCapabilities_preserves_authority` — A subject's authority over an unrelated live object survives another subject's cleanup: as long as the object is not tied to the terminated subject in any of the four ways cleanup checks, the permission stays.
- `cleanupSubject_flushes_translations` — Terminating a subject always models the complete cache-flush the machine needs before any released memory frame may begin a fresh life, leaving the translation cache empty.
- `cleanup_removes_context` — Cleanup erases the terminated subject's saved snapshot from the kernel's bank.
- `cleanup_removes_scheduler_membership` — After cleanup, the terminated subject is neither waiting in the queue nor the running subject.
- `cleanup_terminates_subject` — After cleanup, the terminated subject is no longer a live subject in the permission records.
- `cleanup_live_subject_was_live` — Cleanup can only retire identities, never create them: any subject still live afterwards was already live beforehand.
- `cleanup_live_object_was_live` — Likewise for objects: any object still live after cleanup was already live beforehand.
- `cleanup_object_kind_was_kind` — Any type label an object carries after cleanup — memory, address space, and so on — is the label it already carried before; cleanup can never relabel anything.
- `cleanup_live_object_preserves_kind` — An object that survives cleanup keeps exactly the type label it had before.
- `cleanup_marks_subject_not_runnable` — After cleanup, the terminated subject is marked not runnable, so the scheduler can never pick it again.
- `cleanup_removes_owned_address_space` — Every address space the terminated subject owned is left with no owner at all after cleanup.
- `cleanup_retires_owned_address_space` — Every address-space object the terminated subject owned is fully retired from both record systems, rather than merely left ownerless.
- `cleanup_clears_owned_address_space_handles` — No handed-out permission can keep a destroyed address space reachable: every slot naming it, held by anyone, is cleared in both record systems.
- `cleanup_removes_owned_space_mappings` — Cleanup deletes every page-table mapping inside an address space whose owner was terminated; merely blanking the ownership record would have left stale mappings behind.
- `cleanup_removes_retired_object_mapping` — Cleanup also deletes any page-table entry whose backing object was retired by the termination, even when that entry lives in a different, surviving address space.
- `cleanup_preserves_translationAgreement` — Lifecycle records and translation records are updated as one step, and terminating the currently running subject also clears the recorded active address space.
- `cleanup_preserves_virtualMappingWellFormed` — Every page mapping that survives cleanup is still safe: it has a live owner and a live backing object, matches the authoritative records, and keeps its owner's permission, while anything whose authority was retired is filtered out.
- `cleanup_preserves_virtualLifecycleWellFormed` — Cleanup preserves the entire virtual address-space lifecycle, not just the surviving page mappings; agreement on type labels rules out an address space being accidentally retired through the memory or message-channel cleanup paths.
- `cleanup_preserves_virtualAgreement` — Bookkeeping: after cleanup, the scheduler and the virtual-memory view still share a single permission registry, and that view still satisfies its full lifecycle rules.
- `cleanup_preserves_readyContextAgreement` — Cleanup keeps queue and snapshot bank in step: every queued subject still has a snapshot and every suspended snapshot still belongs to a queued subject, and if removing the last peer leaves a lone running subject, that state stays valid because the next timer tick then refuses cleanly instead of switching.
- `wellFormed_excludes_memory_addressSpace_alias` — In a sound state no single live identifier can be both a piece of owned memory and an address space at once, so terminating a memory owner can never destroy another subject's address space through a name collision — the proof that a real, previously found bug cannot return.
- `cleanup_preserves_resourceKindAgreement` — Cleanup keeps the type-label records consistent, ruling out both ways a surviving resource's label could have been erased: ownership by the terminated subject, or an identifier shared across two different resource kinds.
- `cleanupSubject_preserves_coreWellFormed` — Cleanup preserves the scheduler, snapshot-bank, ownership, and translation-cache portions of the bookkeeping from the pre-state alone; this theorem deliberately stops short of the full claim, which waits until the virtual-lifecycle parts are proved rather than assumed.
- `cleanupSubject_preserves_wellFormed` — Terminating a subject preserves the complete combined bookkeeping in full, even when it leaves a single running subject with an empty queue.
- `resumableDemo_both_legs_agree` — The compact demo routine exported for the boot demonstration gives, on both legs of the worked A-to-B-and-back example, exactly the same packed answer as the full switch model.
- `resumableDemo_cross_substitution_rejected` — Handing the switch A's restore slot with B's owner stamped on it is refused by the very same logic that accepts the genuine B-to-A leg.
- `bounded_round_trip_preserves_a` — A concrete, machine-checked round trip from A to B and back: A's entire suspended return frame and register file survive B's turn untouched, and the third, still-queued subject's snapshot stays separate throughout.
