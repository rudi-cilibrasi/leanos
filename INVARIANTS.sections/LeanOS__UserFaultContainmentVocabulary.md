# One shared fate for every kind of program crash

A user program can go wrong in several distinct ways: dividing by zero, hitting a debugger breakpoint, touching memory it does not have, or poking a forbidden hardware port. These theorems show that all four kinds of failure funnel into one and the same cleanup: the offending program is retired, a surviving peer takes over, and the resulting system state is byte-for-byte identical no matter which failure occurred. Only the recorded reason differs, so no failure type offers a softer landing or a secret path back.

- `contained_entries_normalized` — The kernel's record of a divide-by-zero or breakpoint event carries exactly the reviewed facts, its cause, its user origin, and its error convention, all fixed by the kernel's own manifest and never by any word the program supplied.
- `shared_contained_classes_one_transition` — All four reviewed failure shapes, divide-by-zero, breakpoint, bad memory access, and the denied port poke, drive one shared transition on the same two-program setup: each hands control to the same surviving program, and every resulting system state is byte-for-byte identical, differing only in the recorded reason.
- `kernel_origin_contained_entries_rejected` — A divide-by-zero or breakpoint that appears to come from inside the kernel itself is never given the routine cleanup; the kernel treats it as a fatal condition instead, because these events are only ever expected from user programs.
- `contained_classes_retire_faulting_select_survivor` — For both real crash kinds, the offending program is stripped of its identity, removed from the ready queue and the current slot, and left with no saved state to resume from, while the surviving program is selected to run; there is no way back for the crashed program.
