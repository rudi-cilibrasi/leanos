# The frozen test corpus that cross-checks the generated C code

LeanOS's kernel entry points are exported as generated C functions that take and return plain numbers. This file freezes a single ordered list of 692 test rows — the "oracle" — where the control and optional value expected for each row are computed from the kernel model itself, and the build replays the same rows against the compiled C to catch any divergence introduced by code generation or compilation. The rows and their checks live with their adapter families in the `LeanOS/Oracle/` files, which are checked in parallel; this file lays the families' blocks end to end in their fixed order and pins down where each block starts, so a fact about a position in a family's block is a fact about a fixed corpus row. The corpus is deliberately finite: it is checked evidence about these specific inputs, not a claim about all possible inputs.

- `corpus_shape` — The frozen corpus contains exactly 692 test rows.
- `drop_lengths_flatten` — Bookkeeping: dropping the rows of the first few blocks from a list of blocks laid end to end leaves exactly the remaining blocks laid end to end.
- `rows_at` — Bookkeeping: the corpus rows from the start of any block are that block followed by the blocks after it, so each layout fact below checks one block's starting row instead of re-reading the whole corpus.
- `hosted_boot_transition_class_vectors_exact` — The sixteen test cases at rows 419 through 434 are exactly the grid of boundary inputs for the boot entry point, so the generated code is checked on every combination of the words 0, 1, 2 and the largest 64-bit value.
- `hosted_notify_reply_vectors_exact` — The thirteen test cases at rows 435 through 447 are exactly the notification and reply-permission cases, including the refused ones: signalling without permission, passing on a reply permission, answering a caller that has ended, and answering twice.
- `hosted_user_copy_policy_vectors_exact` — The fourteen test cases at rows 448 through 461 are exactly the user-memory range checks, covering every accepted and refused outcome on the first program's text and stack.
- `hosted_console_authorize_vectors_exact` — The nineteen test cases at rows 462 through 480 are exactly the console-server permission checks: each of the three programs asking for each of the five console and endpoint operations, then requests that name an unknown program or operation.
- `hosted_directory_resolve_vectors_exact` — The twenty test cases at rows 481 through 500 are exactly the name-directory rights checks: an unregistered name, then a registered name with every combination of the four connection rights the directory might hold, then rights words outside those four bits.
- `hosted_fault_handler_vectors_exact` — The eleven test cases at rows 501 through 511 are exactly the fault-handler cases: the one fault handed to the handler, the faults that must take the usual path, the handler's answer, and the refused answers.
- `hosted_device_authorize_vectors_exact` — The twelve test cases at rows 512 through 523 are exactly the keyboard-permission checks of the keyboard-echo image: every program number from 0 to 4 asked about the keyboard and about one other device, then the keyboard holder asked about the largest device number, and the largest possible numbers.
- `hosted_timer_server_vectors_exact` — The sixteen test cases at rows 524 through 539 are exactly the timer-server checks: the server's timer requests at and around the allowed range, timer requests from the other programs, messages to the server from each program, the alarm going off with and without an alarm set, wake-ups by the server and by others, and an unknown request.
- `hosted_frame_server_vectors_exact` — The sixteen test cases at rows 540 through 555 are exactly the frame-server decision checks: the four decisions of the demonstrated run, every kind of hostile decision the kernel must refuse, an accepted take-back and a true "no free page" refusal, an unknown decision, and maximum-size words.
- `hosted_frame_server_view_vectors_exact` — The eight test cases at rows 556 through 563 are exactly the frame-server page-description cases: free pages, a page outside the pool, pages held by this or another program, the "no free page" bit, a decision that names no page, and maximum-size words.
- `hosted_spawn_vectors_exact` — The rows from 564 on begin, by definition, with one row per edge of the spawn family's boot dispatcher table, in table order, followed by its fourteen hostile encodings.
- `hosted_spawn_syscall_vectors_exact` — The rows from 632 on begin, by definition, with the spawn system call's rows: the demonstration image's calls, every kind of refusal, and the value words.
- `hosted_loader_vectors_exact` — The rows from 668 to 691 are by definition the loader's rows: its source checks and its decisions.
- `hosted_mixed_vectors_exact` — Rows 314 through 336 of the corpus are, by definition, the dispatcher's complete canonical mixed-scenario edge set itself — not a second hand-maintained table that could drift out of step.
- `hosted_budget_vectors_exact` — The 24 rows beginning at row 359 are exactly the frame-budget scenario's row list.
- `hosted_iotlb_publication_vectors_exact` — The nine rows beginning at row 383 are exactly the fixed IOTLB publication sequence, including the exact completion and all stale or wrong-scope negatives.
- `hosted_capability_transfer_boot_vectors_exact` — Rows 392 through 397 are exactly the dedicated boot capability-transfer trace, including its explicit subject switch and both state-preserving authority denials.
- `hosted_inFlight_revocation_vectors_exact` — The oracle records from row 398 on are, by definition, the eleven-edge in-flight revocation trace and its three hostile records, followed by the blocking-IPC, boot-transition, console-server, and later records through the spawn family, not a second hand-written table.
- `hosted_scalar_vectors_exact` — The first 86 rows of the corpus are exactly the boot, system-call, messaging, preemption, boot-allocation, return-to-user, blocking-message, and capability-reuse rows, so their position in that family's block is their corpus row.
- `hosted_interrupt_vectors_exact` — The 206 rows beginning at row 86 are exactly the interrupt, entry, fault, port, non-maskable-interrupt, boot-phase, stale-translation, and page-fault rows, so position `i` of that family's block is corpus row 86 + `i`.
- `hosted_composite_scenario_vectors_exact` — The 22 rows beginning at row 292 are exactly the stateful dispatcher's scenario and hostile-encoding rows.
- `composite_inFlight_revocation_values_zero` — No record from the in-flight revocation trace up to the spawn family publishes a value word: the cancelled child never becomes a returned handle.
- `hosted_invalidation_vectors_exact` — Rows 337 through 355 are exactly the stateful cache-invalidation protocol walk, including the independent unmap and switch-away/back branches, and rows 356 through 358 are its three deliberately bad requests: a malformed effect, a mismatched state, and a replayed stale ticket.
- `composite_result_values_exact` — Before the spawn family exactly two corpus rows have a nonzero value word, the accepted attached receipt in each independently modeled transfer trace (`0x60003`); in the spawn family exactly ten do: the two kernel grants, the four accepted spawns, two frame grants, and two terminations.
- `interrupt_entry_adapter_agrees_with_model` — On every interrupt-entry row anywhere in the corpus, the exported adapter's answer equals the answer of the richer entry model.
- `fault_dispatch_adapter_agrees_with_model` — Every fault-dispatch row couples the exported allocation-free adapter to an expectation computed by the authoritative chain of entry normalization, lifecycle cleanup, scheduler selection, saved-context banking, and translation-cache transition.
- `user_return_adapter_agrees_with_model` — On every return-to-user row anywhere in the corpus, the exported adapter agrees with the authoritative validator.
- `hosted_loader_trace_vectors_exact` — The last rows, from 692 on, are by definition the loader's answers along the loader demo.
