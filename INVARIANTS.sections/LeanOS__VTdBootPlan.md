# Setting up the IOMMU at boot (VT-d plan)

The IOMMU is the chip that polices which parts of memory each device may touch, and it makes its decisions by walking lookup tables the kernel installs before switching it on. These theorems pin down that boot-time plan exactly: one compiler builds every table the kernel installs, a plan with no device assignment denies every device, a plan with one assignment gives that device exactly the memory pages the kernel's ownership records grant it and nothing else, the byte layout of each table entry is an exact two-way translation with no ambiguity, and the switch-on procedure is checked step by step so that a reordered, skipped, or tampered activation is caught rather than silently accepted.

- `physicalFrameLimit_value` — Spelling out the definition: the largest memory-frame number the plan will ever accept is exactly 1,099,511,627,776, matching the machine's addressable range.
- `domainLimit_value` — Spelling out the definition: the number of distinct protection domains the tables can name is exactly 65,536.
- `decode_encode_root` — Writing a well-formed top-level table entry into its raw hardware words and reading it back returns exactly the entry you started with.
- `encode_decode_root` — Every raw word pair the top-level decoder accepts is precisely what the encoder would have produced, so there are no acceptable-but-unwritable entries and no hidden extra bit patterns.
- `root_entry_encoding_injective` — Two different well-formed top-level entries can never share the same raw hardware words, so a word in memory pins down one entry unambiguously.
- `decode_encode_context` — Writing a well-formed per-device table entry into its raw hardware words and reading it back returns exactly the entry you started with.
- `encode_decode_context` — Every raw word pair the per-device decoder accepts is precisely what the encoder would have produced, so acceptance and encoding describe the same set of entries.
- `context_entry_encoding_injective` — Two different well-formed per-device entries can never share the same raw hardware words.
- `decode_secondLevelEntry` — Writing a second-stage table entry for a frame with at least one of read or write permission and reading it back returns exactly that frame and permission.
- `compile_deterministic` — Compiling the same boot input twice always produces the same plan or the same rejection; the compiler has no randomness or hidden state.
- `compile_source` — Bookkeeping: an accepted plan is built from exactly the input it was compiled from, so every table it emits is a function of that checked input.
- `checks_pass` — Bookkeeping: if the compiler accepts an input, every one of its rejection checks came out clean for that input.
- `grantChecks_pass` — Bookkeeping: if the compiler accepts an input that binds a device, every check specific to that device's grants came out clean.
- `accepted_state_deny_all` — A plan without a device binding is only accepted when the kernel's device-ownership records themselves list no device assignments and no memory grants.
- `accepted_context_entries_absent` — When the plan carries no device binding, every one of the 256 per-device slots is absent, so no device is authorized to touch any memory.
- `accepted_requesters_bound_once` — In an accepted plan each device identity is looked up through exactly one table slot, with exactly 256 slots in total, so no device can answer through a second, forgotten entry.
- `accepted_maps_no_frame` — When the plan carries no device binding, no memory frame whatsoever is reachable: no per-device entry is present, so there are no second-stage tables to walk at all.
- `accepted_root_shape` — An accepted plan's top-level table has exactly one live entry, pointing bus 0 at the reserved per-device table, and every other entry is absent.
- `accepted_table_frames_distinct` — All table frames of an accepted plan (top-level, per-device, and the three second-stage tables when a device is bound) are pairwise different, so writing one table can never overwrite another.
- `accepted_tables_distinct` — An accepted plan never stores its two tables in the same memory frame, so writing one can never corrupt the other.
- `accepted_table_frames_bounded` — Every table frame of an accepted plan is a real, nonzero frame inside the machine's addressable range.
- `accepted_reservation_checked` — Every accepted plan has checked every memory frame holding one of its tables, including the second-stage tables of an assigned device, against the boot-time memory reservation list.
- `accepted_cpu_tables_disjoint` — Every accepted plan has checked that none of its table frames, including the second-stage tables of an assigned device, overlap the processor's own page tables.
- `accepted_agrees_with_domain_projection` — A plan without a device binding agrees with the kernel's own authority ledger: no matter which device identity or generation you ask about, the ledger resolves to no live assignment.
- `pair_words_length` — Bookkeeping: laying a list of table entries out as low-word/high-word pairs always yields exactly twice as many words as entries.
- `pair_words_getElem?` — Bookkeeping: in a list of entries laid out as low-word/high-word pairs, word 2i is the low word of entry i and word 2i+1 is its high word.
- `accepted_root_words_length` — Bookkeeping: the raw top-level table an accepted plan emits is exactly 512 words, two per entry for all 256 entries.
- `accepted_context_words_length` — Bookkeeping: the raw per-device table an accepted plan emits is exactly 512 words, two per entry for all 256 entries.
- `grantedPage_some` — If the granted-pages specification gives a frame and permission for a page, then some mapping in the kernel's ownership records covers that page, carries that permission, and names that frame.
- `accepted_grant_pages_bounded` — In an accepted plan every granted page lies inside the single last-level table and carries a nonempty permission.
- `grantedPage_none_of_large` — In an accepted plan no page at or beyond the 512-entry last-level table is granted.
- `secondLevelPage_getElem?` — Bookkeeping: a second-stage table page with a single entry reads back that entry at its slot and zero everywhere else.
- `decode_zero_secondLevel` — An all-zero second-stage entry is never treated as present.
- `intersect_readWrite` — Bookkeeping: combining a permission with two read/write upper-level entries leaves it unchanged.
- `walkSecondLevel_exact` — Walking the three second-stage tables an accepted plan emits yields, for every page, exactly the frame and permission the granted-pages specification gives, and nothing for pages that were not granted.
- `pair_wordAt` — Bookkeeping: reading word 2i or 2i+1 of a paired table layout returns the low or high word of entry i, or zero past the end.
- `context_word_decode` — Bookkeeping: if a plan's per-device slot holds a well-formed entry, decoding the two raw words at that slot returns exactly that entry.
- `accepted_requester_bound` — In an accepted plan the bound device sits on bus 0, inside the 256-slot per-device table the single top-level entry points to.
- `accepted_assignment_domain_bound` — In an accepted plan the protection domain written into the bound device's entry fits the hardware's 16-bit domain field.
- `accepted_translation_exact` — The central fact: for every device identity and every page, walking the raw tables an accepted plan emits yields exactly the memory frame and permission the kernel's ownership records grant that device for that page, and nothing at all where nothing was granted. This is about the encoded tables, not about how the IOMMU hardware walks them.
- `accepted_unbound_translates_nothing` — A plan with no device binding gives no device access to any page.
- `translation_grant` — Bookkeeping: any translation the raw tables yield belongs to the bound device and comes from the granted-pages specification.
- `accepted_translation_from_grant` — Every translation the raw tables yield comes from one real grant: the bound device, a page inside that grant's address range, the grant's own permission, and the frame its offset names.
- `accepted_translation_avoids_protected` — No translation the raw tables yield reaches a protected frame: every reachable frame is in range and outside the kernel's own reservations, the processor's page tables, and the IOMMU tables themselves.
- `accepted_grant_translates` — Every page a grant covers really is translated for the bound device, so the tables never silently drop granted access.
- `decoded_validation_deterministic` — Re-checking the live IOMMU against the plan gives the same verdict every time it is run on the same reading; the checker has no randomness or hidden state.
- `stepTag_injective` — Every distinct step of the activation procedure gets its own distinct numeric tag, so no two steps can ever be confused in the activation journal.
- `canonicalJournalUInt64_toNat` — Bookkeeping: the fixed constant the running system compares journals against is exactly the encoded form of the one correct eight-step activation sequence.
- `validateActivation_alignment_matches_pageBytes` — A stepping-stone fact used to tie two views together: the alignment test the activation checker performs on a table address agrees exactly with alignment on the page size used everywhere else in the model.
- `assignedEDUTransferScalar_refines_authoritative_scenario` — For the fixed assigned-EDU scenario, the allocation-free scalar boundary returns exactly the same verdict as the authoritative transfer model for both allowed directions and the reviewed wrong-direction, boundary-crossing, and wrong-source denials.
- `validateActivation_deterministic` — The final activation check, run on the same ten observed hardware values, always returns the same accept-or-reject code; there is no randomness or hidden state.
- `deviceServiceState_shape` — The device-service IOMMU grant is accepted and is the only authority it creates: one assignment for the assigned USB controller holding a single read/write window of four model pages. The boot tables for it are compiled from this state like every other plan, so the general translation theorem applies to them.
- `deviceServiceTransfer_window` — Under that grant the USB controller may read and write anywhere inside its window, and nothing else: a transfer that starts below it, runs past its end, or comes from another device or an older assignment is refused.
