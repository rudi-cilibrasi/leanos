# Copying and revoking authority keeps every view in step

Capabilities are the kernel's unforgeable permissions. These theorems show that copying a capability, revoking it, revoking a whole family of derived capabilities, and creating a program publish one capability state to every part of the kernel at once and preserve the global runtime invariant.

- `gate_capabilityCopy_accepted_synchronizes` — When a permission is successfully copied to another program, every part of the kernel sees the new permission store at once; success can never be reported while the scheduler, messaging, mapping, or saved-context views still hold the old one.
- `gate_capabilityCopy_accepted_preserves_runtimeWellFormed` — An accepted permission delegation keeps every other resource exactly as it was, keeps all authority that memory mappings already rely on, keeps every pending sealed identity out of live slots, and preserves whole-kernel consistency.
- `installRevokedCapabilities_preserves_runtimeWellFormed` — Deleting permission slots is globally safe as long as the program roster, the history, and the authority that live resources still depend on are all retained; both direct and lineage-wide revocation reuse this shared fact.
- `gate_createSubject_accepted_synchronizes` — Creating a new program publishes its fresh identity to every lifecycle and permission view of the kernel in one coherent step, and the published state itself satisfies the lifecycle rules.
- `gate_capabilityRevoke_accepted_synchronizes` — An accepted revocation of one permission slot is seen identically by every consumer of the permission store, and the resulting state remains internally consistent.
- `gate_capabilityRevokeSubtree_accepted_synchronizes` — Accepted revocation of a permission together with everything derived from it is published in one step, so no scheduler, messaging, or saved-context view is left looking at stale authority.
- `gate_capabilityRevoke_accepted_preserves_runtimeWellFormed` — Accepted single-slot revocation keeps the whole kernel consistent provided the removed slot was not the last authority backing a live mapping or address-space ownership, and success is reported in the same step.
- `gate_capabilityRevokeSubtree_accepted_preserves_runtimeWellFormed` — The same safety boundary holds for revoking an entire permission lineage; clearing the extra descendants can never make a pending sealed identity suddenly live.
- `gate_capabilityRevoke_rejected_atomic` — A refused direct revocation changes nothing at all, so every piece of kernel bookkeeping is untouched.
- `gate_capabilityRevokeSubtree_rejected_atomic` — A refused lineage revocation is likewise a pure no-op on the kernel state.
- `gate_capabilityRevokeSubtree_accepted_cancels_sealed_descendants` — An accepted whole-family take-back through the composite gate also cancels every sealed in-flight descendant of that family: its in-flight record, its transfer mailbox entry, and its IPC mailbox entry vanish in the same step.
- `gate_capabilityRevokeSubtree_accepted_authority_monotone` — After an accepted whole-family take-back, no in-flight permission and no installed permission descends from the taken-back root: authority strictly decreases across both representations.
- `gate_capabilityRevokeSubtree_accepted_retains_history` — An accepted whole-family take-back leaves lineage history and the identity counter unchanged, so a cancelled identity can never be reissued.
- `gate_capabilityRevokeSubtree_accepted_preserves_unrelated` — An accepted whole-family take-back leaves unrelated in-flight permissions, parked messages, installed slots, the ready queue, the current program, saved continuations, mappings, and the execution context exactly as they were.
- `syscall_result_sound` — A completed system call's reply is exactly the one computed for the caller and address space the kernel itself selected; the request has no way to smuggle in a different identity.
- `ipc_result_sound` — A completed messaging call likewise runs only under the kernel's own record of who is executing; there is no public way to supply a different trusted context.
- `capability_copy_result_sound` — Permission checks during copying are always evaluated for the program the kernel says is running, because the public operation has no field for naming anyone else.
- `map_result_sound` — Both the authority and the target address space for a mapping request come from the kernel's live execution context, never from words the caller supplies.
- `authority_operations_result_sound` — Every public operation that can read or change authority is confined to the program the kernel selected: callers can pick handles, slots, rights, pages, and payload words, but never the actor or the active address space.
