# Resource guarantees for every kernel step and every run

The previous section proved the resource guarantee (the identity counters bound every identity ever issued, the frame table only names real, issued frames, and unwritten frames hold wiped contents) for the steps that leave the subject records and memory alone. This section proves it for every remaining step of the kernel: interrupt cleanup, user system calls, timer switches, permission reduction, both kinds of termination, every scheduler step, the blocking message operations, the deferred-cancellation drain, and the translation-invalidation steps. Two steps need a stated condition: creating a subject under a caller-chosen identity, and completing an unmap of the running address space. The section then proves the guarantee along whole runs of steps: it holds at the end, no identity is ever created twice by either way of creating subjects, terminated identities are never reused, and every subject's frame allowance and usage stay exactly the same.

- `Scheduler.selectNext_issuedSubjects` — Picking the next subject to run never changes the record of which subject identities have ever been issued.
- `Scheduler.tick_issuedSubjects` — A scheduler timer tick never changes the record of issued subject identities.
- `Scheduler.remove_issuedSubjects` — Taking a subject off the run queue never changes the record of issued subject identities.
- `ResumablePreemption.switch_history` — A timer-driven switch between programs, whatever its outcome, keeps the record of issued subject identities and leaves the memory state seen by the address-translation view unchanged.
- `ResumablePreemption.remove_history` — Removing a subject together with its saved context, whatever the outcome, keeps the record of issued subject identities and the memory state seen by the address-translation view.
- `Scheduler.selectNext_eq_issuedSubjects` — Bookkeeping: the same fact as picking the next subject, stated for a named result.
- `BlockingIPC.receiveOrBlock_issuedSubjects` — A blocking receive never changes the record of issued subject identities.
- `BlockingIPC.send_issuedSubjects` — A blocking send never changes the record of issued subject identities.
- `BlockingIPC.cancelSubject_issuedSubjects` — Cancelling a waiting receiver never changes the record of issued subject identities.
- `BlockingIPC.cancelSubjectTyped_issuedSubjects` — The typed form of cancelling a waiting receiver never changes the record of issued subject identities.
- `BlockingIPCContext.receiveOrBlock_issuedSubjects` — A blocking receive that also saves the caller's context never changes the record of issued subject identities.
- `BlockingIPCContext.send_issuedSubjects` — A blocking send that may release a saved receiver context never changes the record of issued subject identities.
- `BlockingIPCContext.cancel_issuedSubjects` — Cancelling a waiter together with its saved context never changes the record of issued subject identities.
- `BlockingIPCContext.drainDeferred_issuedSubjects` — Returning a deferred, cancelled waiter to the run queue never changes the record of issued subject identities.
- `VirtualHistoryAgrees.refl` — Bookkeeping: every memory state agrees with itself on the histories the resource guarantee reads.
- `VirtualHistoryAgrees.of_memory` — Bookkeeping: two memory states with the same memory record and the same history of issued address spaces agree on everything the resource guarantee reads.
- `resourceHistoryAgrees_of` — Bookkeeping: two kernel states agree on everything the resource guarantee reads once they agree on the counters, the frame table, the frame contents, the subject history, and the memory histories.
- `ResourceHistoryAgrees.trans` — Bookkeeping: agreement on everything the resource guarantee reads carries across two consecutive steps.
- `Syscall.dispatch_virtualHistory` — Every user system call, accepted or refused, leaves the memory record and the history of issued address spaces unchanged; mapping and unmapping change only page mappings.
- `TLB.protect_virtualHistory` — Reducing a page's permissions leaves the memory record and the history of issued address spaces unchanged.
- `publishBlockingIPCContext_historyAgrees` — Publishing a blocking-message state whose subject records keep the issue history keeps everything the resource guarantee reads; it does not touch memory.
- `restoreBlockingPeer_historyAgrees` — Handing the processor to the next program after a receiver blocks keeps everything the resource guarantee reads, given the same condition on the published subject records.
- `publishReleasedBlockingContext_historyAgrees` — Making a woken or cancelled receiver runnable again keeps everything the resource guarantee reads, given the same condition on the published subject records.
- `CompositeState.Coherent.resumableLifecycle` — When the kernel's views agree, the saved-context view sees exactly the kernel's subject records.
- `CompositeState.Coherent.resumableVirtual` — When the kernel's views agree, the address-translation view sees exactly the kernel's memory state.
- `installTerminatedResumable_cleanup_historyAgrees` — Publishing a subject's cleanup keeps everything the resource guarantee reads: termination keeps the subject history, and cleanup changes only permissions, owners, and mappings, never the memory record's histories, frames, or bindings.
- `installTerminatedSubject_historyAgrees` — Publishing an explicit termination keeps everything the resource guarantee reads.
- `publishInterruptCleanup_historyAgrees` — Cleaning up a subject after a contained fault keeps everything the resource guarantee reads.
- `installResumable_historyAgrees` — Publishing a saved-context state keeps everything the resource guarantee reads, provided its subject records keep the issue history and its memory keeps the memory histories.
- `installVirtualMemory_historyAgrees` — Publishing a mapping-only change keeps everything the resource guarantee reads, provided the new memory keeps the memory histories.
- `selectLiveReturnAuthority_historyAgrees` — Choosing how to return to a program changes only the execution latch, so everything the resource guarantee reads is kept.
- `dispatchBlockingReceive_historyAgrees` — A blocking receive through the kernel state, whatever its outcome, keeps everything the resource guarantee reads.
- `dispatchBlockingSend_historyAgrees` — A blocking send through the kernel state, whatever its outcome, keeps everything the resource guarantee reads.
- `dispatchBlockingCancel_historyAgrees` — Cancelling a blocked receiver through the kernel state, whatever the outcome, keeps everything the resource guarantee reads.
- `drainDeferredCancellation_historyAgrees` — Returning a deferred, cancelled waiter through the kernel state, whatever the outcome, keeps everything the resource guarantee reads.
- `historyAgrees_of_frames` — A step that respects a declared write set and writes none of the counters, the frame table, the frame contents, the subject records, or the memory state keeps everything the resource guarantee reads.
- `applyOperation_historyAgrees_of_framed` — An ordinary kernel operation that writes neither the subject records nor the memory state keeps everything the resource guarantee reads.
- `applyOperation_historyAgrees_of_coherent` — From a state whose views agree, every ordinary kernel operation except creating a subject under a caller-chosen identity keeps everything the resource guarantee reads.
- `gate_stutters_or_applies` — The ordinary kernel gate either leaves the state unchanged or performs exactly the requested operation.
- `authoritativeGate_historyAgrees` — Every step of the full kernel gate except caller-chosen subject creation keeps the counters, the frame table, the frame contents, the subject history, both object histories, the frame allocator, and every memory binding, from any state satisfying the whole-kernel guarantee.
- `authoritativeGate_createSubject_history` — Creating a subject under a caller-chosen identity changes none of what the resource guarantee reads except that the subject history may gain exactly that identity, which was not in it before.
- `resourceWellFormed_of_added_subject` — A step that keeps everything else the resource guarantee reads and adds one positive subject identity below the subject counter to the history keeps the resource guarantee.
- `authoritativeGate_createSubject_preserves_resourceWellFormed` — Creating a subject under a caller-chosen identity keeps the resource guarantee when that identity is positive and below the subject counter.
- `authoritativeGate_createSubject_requires_bound` — That condition is necessary: if caller-chosen creation adds its identity and the counters still bound every issued identity afterwards, the identity was positive and below the counter.
- `InvalidationOperation.apply_historyAgrees` — Every translation-invalidation step except completing an unmap of the running address space keeps everything the resource guarantee reads.
- `authoritativeAcknowledgeCurrentUnmap_historyAgrees` — Completing an unmap of the running address space keeps everything the resource guarantee reads, provided the pending result it installs keeps the memory histories.
- `StaleTranslation.step_unmap_virtualHistory` — A pending unmap computed by the invalidation protocol keeps the memory record and the history of issued address spaces.
- `authoritativePrepareCurrentUnmap_pendingHistoryAgrees` — Preparing an unmap of the running address space, from a state whose invalidation view matches the kernel's translations, leaves a pending result that keeps the memory histories.
- `InvalidationOperation.apply_preserves_authoritativeRuntimeWellFormed` — Every translation-invalidation step except completing an unmap of the running address space keeps the whole-kernel guarantee.
- `authoritativeGate_preserves_resourceRuntimeWellFormed` — Every step of the full kernel gate except caller-chosen subject creation keeps the combined guarantee, with no other condition; this covers interrupt cleanup, system calls, timer switches, permission reduction, termination, scheduling, blocking messages, and the deferred drain.
- `authoritativeGate_createSubject_preserves_resourceRuntimeWellFormed` — Caller-chosen subject creation keeps the combined guarantee when its identity is positive and below the subject counter.
- `InvalidationOperation.apply_preserves_resourceRuntimeWellFormed` — Every translation-invalidation step except completing an unmap of the running address space keeps the combined guarantee.
- `authoritativeAcknowledgeCurrentUnmap_preserves_resourceRuntimeWellFormed` — Completing an unmap of the running address space keeps the combined guarantee when its stated condition holds.
- `currentUnmapAdmissible_of_prepared` — On the established path of preparing and then completing an unmap of the running address space, from a state whose invalidation view matches the kernel's translations, the completion's condition always holds.
- `CompositeStep.admissible_of_unconditional` — Every step other than caller-chosen creation and the running-space unmap completion meets its condition in every state.
- `CompositeStep.admissible_preserves` — Every kernel step, in a state where its condition holds, keeps the combined guarantee.
- `ResourceHistoryAgrees.grows` — Bookkeeping: a step that keeps everything the resource guarantee reads also only grows the subject history.
- `ResourceHistoryGrows.trans` — Bookkeeping: keeping the frame table and memory histories while only growing the subject history carries across two consecutive steps.
- `authoritativeGate_createSubject_grows` — Caller-chosen subject creation keeps the frame table and the memory histories and only adds to the subject history.
- `lifecycleGate_grows` — Counter-drawn subject creation keeps the frame table and the memory histories and only adds to the subject history.
- `CompositeStep.admissible_grows` — Every kernel step whose condition holds keeps the frame table and the memory histories and only adds to the subject history.
- `CompositeStep.created_fresh` — An identity a step creates, by either way of creating subjects, was not in the subject history before the step and is in it afterwards.
- `admissibleAlong_of_unconditional` — A run made only of steps that need no condition meets every step's condition from any starting state.
- `runSteps_admissible` — Along a run whose steps each meet their condition, the combined guarantee holds at the end and the subject history only grows.
- `createdAlong_fresh` — Along such a run no identity is created twice, and every created identity was outside the starting history and is in the final one.
- `ResourceHistoryGrows.budget` — A step that keeps the frame table and memory histories leaves every subject's frame usage and allowance exactly unchanged.
- `authoritativeGate_budget_exact` — No step of the full kernel gate, termination and caller-chosen creation included, changes any subject's frame usage or allowance.
- `authoritativeGate_termination_accounts` — Terminating a subject, terminating the running subject, and cleaning up after a contained fault keep both identity counters and the whole subject history, so a terminated identity stays recorded as issued and below the counter, and they leave every subject's frame usage and allowance unchanged.
- `composite_resource_trace` — Along any run of kernel steps that each meet their condition, starting where the combined guarantee holds: the guarantee holds at the end, no identity is created twice and none issued before the run is created again, counter-drawn identities strictly increase, the subject history only grows, and every subject's frame usage and allowance are unchanged and usage stays within the allowance.
- `issued_never_recreated` — Along any such run, an identity already recorded as issued, such as a terminated one, is never created again, neither from the counter nor under a caller-chosen identity.
- `composite_resource_trace_unconditional` — For runs that avoid caller-chosen creation and the running-space unmap completion, the guarantee, unique creation, and unchanged frame budgets hold with no condition on the steps.
