# Identity issuers, frame budgets, and frame contents inside the kernel state

The kernel state now also holds the two counters that hand out never-reused subject and object identities, the fixed table saying which physical frames each subject may use, and the frame-contents record used to prove that reused frames are wiped. None of these parts brings its own copy of memory: each is read against the kernel's single record of memory and subjects. Subject creation can now draw its identity from the counter instead of trusting a caller-supplied number, and the theorems here prove that this creation is all-or-nothing, never reuses an identity, and gives the new subject a zero frame allowance.

- `resourceWellFormed_iff` — Spelling out the definition: the new resource guarantee is exactly its four promises about the counters, the counters bounding every identity ever issued, the frame table, and wiped frame contents.
- `resourceWellFormed_preserved_of_frames` — A step that respects a declared write set keeps the resource guarantee once the promises reading something it writes are proved again; all the others carry over automatically.
- `resourceWellFormed_preserved_of_untouched` — A step that writes none of the counters, the frame table, the frame contents, the subject records, or the memory state keeps the resource guarantee with no further proof.
- `resourceRuntimeWellFormed_iff_all` — The combined guarantee, the existing whole-kernel guarantee plus the resource guarantee, is exactly one list of separately stated promises, each with the parts of the kernel state it reads.
- `Operation.footprint_unread_resources` — No ordinary kernel operation declares that it reads, let alone writes, the identity counters, the frame table, or the frame contents.
- `AuthoritativeOperation.footprint_unread_resources` — No operation of the full kernel gate, including the blocking message operations and the deferred-cancellation drain, declares that it reads the identity counters, the frame table, or the frame contents.
- `InvalidationOperation.footprint_unread_resources` — No translation-invalidation step declares that it reads the identity counters, the frame table, or the frame contents.
- `untouched_of_unread` — Bookkeeping: a part of the kernel state that a step does not read is a part it does not write.
- `authoritativeGate_resources` — Every outcome of the full kernel gate leaves the identity counters, the frame table, and the frame contents exactly as they were.
- `InvalidationOperation.apply_resources` — Every translation-invalidation step leaves the identity counters, the frame table, and the frame contents exactly as they were.
- `authoritativeGate_preserves_resourceWellFormed_of_framed` — A kernel-gate operation that writes neither the subject records nor the memory state keeps the resource guarantee, by the frame rule alone.
- `resourceFramed_ordinary` — Message passing, the non-maskable-interrupt path, choosing and completing a return to a program, adding a subject to the run queue, and restart write neither the subject records nor the memory state.
- `InvalidationOperation.apply_preserves_resourceWellFormed` — Every translation-invalidation step except completing an unmap of the running address space keeps the resource guarantee, by the frame rule alone.
- `bootRuntime_resourceWellFormed` — The kernel state produced at boot satisfies the resource guarantee: nothing has been issued, no frame is assigned to a subject, and nothing is bound.
- `bootRuntime_resourceRuntimeWellFormed` — Once the boot page-table plan is accepted, the boot kernel state satisfies the combined guarantee.
- `issueSubject_accepted_state` — Spelling out the definition: when the counter hands out an identity and creation accepts it, the new kernel state is exactly the published subject creation with the counter advanced.
- `issueSubject_exhausted_unchanged` — If the subject-identity counter is used up, creation changes nothing at all, both counters included.
- `issueSubject_rejected_unchanged` — If creation is refused, nothing at all changes, both counters included.
- `issueSubject_exhausted_iff` — Creation reports a used-up counter exactly when the subject-identity counter is used up, and for no other reason.
- `issueSubject_issued` — A successful creation hands out exactly the counter's previous value, which is a representable identity, advances the counter by one, and performs exactly the kernel's ordinary subject creation for that identity.
- `issueSubject_total` — While the guarantee holds and the counter is not used up, creation always succeeds with the counter's next value: that identity can never be refused as already used or already live.
- `issueSubject_refines` — Creation through the kernel state gives the same result, the same counters, the same subject records, and the same mailboxes as the standalone bounded-identity model, apart from republishing the updated permission table to the memory view.
- `issueSubject_fresh` — An identity handed out by successful creation had never been issued and was not live beforehand, and is issued and live afterwards.
- `issueSubject_frames` — Counter-drawn subject creation changes nothing outside its declared write set, whatever the outcome.
- `lifecycleGate_frames` — Every outcome of the counter-drawn creation gate, including refusals while busy or halted, changes nothing outside the declared write set.
- `issueSubject_reads` — Counter-drawn subject creation reads only what it declares: two kernel states that agree there get the same result and agreeing new states on everything it writes.
- `lifecycleGate_reads` — The counter-drawn creation gate reads only what it declares, including the execution mode, so two kernel states that agree there get the same result and agreeing new states.
- `AuthoritativeRuntimeWellFormed.withIssuers` — Changing only the identity counters keeps the existing whole-kernel guarantee, because none of its promises reads them.
- `issueSubject_preserves_authoritativeRuntimeWellFormed` — While the kernel is running normally, counter-drawn creation keeps the existing whole-kernel guarantee.
- `issueSubject_preserves_resourceWellFormed` — Counter-drawn creation keeps every resource promise: the new identity is the old counter value, which the advanced counter now bounds, and memory, frames, the frame table, and frame contents are untouched.
- `lifecycleGate_preserves_resourceRuntimeWellFormed` — Every outcome of the counter-drawn creation gate keeps the combined guarantee.
- `lifecycleGate_unchanged_of_not_issued` — Whenever the counter-drawn creation gate does not hand out an identity (used-up counter, refusal, busy or halted kernel), the whole kernel state is unchanged.
- `budget_conservation` — In every kernel state, each subject uses no more frames than its allowance, each frame is assigned to at most one subject, and every modeled frame is in exactly one of the reserved, free, or owned classes.
- `budget_eq_of_allocator` — A subject's frame usage and allowance depend only on the frame table and the frame allocator.
- `authoritativeGate_budget_unchanged` — Every kernel-gate step that does not write the memory state leaves every subject's frame usage and allowance exactly unchanged.
- `issueSubject_budget_unchanged` — Counter-drawn subject creation leaves every subject's frame usage and allowance exactly unchanged.
- `issueSubject_zero_budget` — A subject created from the counter starts with a frame allowance of zero and uses no frames, because the frame table only assigns frames to subjects issued earlier.
- `ResourceHistoryAgrees.refl` — Bookkeeping: every kernel state agrees with itself on everything the resource promises read.
- `resourceWellFormed_of_historyAgrees` — A new state that keeps the counters, the frame table, the frame contents, both issue histories, the frame allocator, and every memory binding keeps the resource guarantee.
- `VirtualMapping.map_registry` — Mapping a page changes neither the memory record nor the history of issued address spaces.
- `VirtualMapping.unmap_registry` — Unmapping a page changes neither the memory record nor the history of issued address spaces.
- `applyOperation_historyAgrees` — Copying, revoking, and transferring permissions, and mapping and unmapping pages, change no issue history, frame state, or memory binding.
- `authoritativeGate_preserves_resourceWellFormed_of_keepsHistory` — Every kernel-gate outcome of a permission copy, revocation, transfer, map, or unmap keeps the resource guarantee.
- `CompositeStep.apply_issuers` — Each step either leaves the identity counters alone or hands out exactly the subject counter's current, representable value and advances it by one; the object counter never changes.
- `runSteps_subject_monotone` — Along any sequence of steps the subject-identity counter never goes down and the object counter never changes.
- `issuedAlong_strictly_increasing` — Along any sequence of steps the subject identities handed out strictly increase, so none is ever handed out twice, and each lies between the starting and the final counter value.
- `runSteps_exhausted_absorbing` — Once the subject-identity counter is used up, it stays used up and unchanged along any sequence of steps, and no identity is handed out.
- `CompositeStep.preserving_lifecycle` — Counter-drawn creation is a step that keeps the combined guarantee.
- `CompositeStep.preserving_of_framed` — A kernel-gate operation that writes neither the subject records nor the memory state is a step that keeps the combined guarantee.
- `CompositeStep.preserving_of_keepsHistory` — Permission copy, revocation, transfer, map, and unmap are steps that keep the combined guarantee.
- `composite_identity_no_reuse` — Along any sequence of guarantee-keeping steps starting from a state that satisfies the combined guarantee: the guarantee still holds at the end, the identities handed out strictly increase, each lies above every subject identity ever issued before the sequence began, and a used-up counter stays used up.
