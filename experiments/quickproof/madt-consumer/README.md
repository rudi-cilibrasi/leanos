# QuickProof project 5: the Qotom MADT consumer's caller obligations (#608)

This experiment proves that LeanOS's Qotom MADT consumer keeps the caller
obligations of [the review](../../../docs/qotom-madt-consumer-review.md),
against any answers of the Lean exports it calls. It uses
[QuickProof](https://github.com/genproof/quickproof-public) v0.1.0 (Coq 8.20.1,
VST 2.15, CompCert 3.15) on
[`include/qotom_bsp_consumer.h`](../../../include/qotom_bsp_consumer.h).

`qotom_bind_validated_madt_entries` is the C between three Lean exports
(`docs/qotom-bsp-consumer.md`). It streams the MADT's entry bytes through the
generated byte step, sixteen projections per byte, and walks the records. It
asks the generated NMI policy, then the generated BSP finish, and publishes
the result. The Lean theorems of `LeanOS.QotomMadtStream` say what the
answers mean. This theorem is about the C between them: that it asks exactly
the questions the review requires, carries the answers unchanged, and
publishes exactly what they decide. The explicit Qotom production candidate
calls it from `boot_allocate`. The theorem is about the C source under
CompCert's semantics for x86-64, for every input the law allows. The decision
record is ADR 0030, with its #608 amendment.

The code was not provable as written: it returned `struct qotom_bsp_result`
by value, which `clightgen` refuses (the pilot's survey, ADR 0030 refactor 1).
Issue #608 made it return the status and write the result through a pointer,
and route every exit through one publishing helper. Statuses, details,
offsets, calls and published values are unchanged.

## The law

The law is a C program in [`project/harness/`](project/harness/). Its first
comment states the claim, and that comment, not this summary, is what a reader
must review.

**`consumer_obligations`: the consumer's whole behaviour, against any Lean.**
The harness supplies the three exports itself: an adversarial Lean that
answers every call with any 64-bit value, a different one each time, and
checks each call against the review. The span may hold any bytes and have any
length; each of the span, the observation and the result record may be NULL.
For every such input the consumer:

- reads only the span and the observation, and writes only the result
  record;
- with no result record returns 1 and calls nothing; with an absent span or
  observation, or a length outside 1 to 65536 − 44, publishes the
  input-bounds rejection and calls nothing;
- calls the stream step exactly sixteen times per byte, in order, all with one
  unchanged old state and that byte, starting from the initial state and then
  from projections 3 to 14 of the previous byte's answers;
- goes to the next byte only when the answers accept the transition, and
  otherwise publishes the rejection the review names and calls nothing more;
- after the stream walks the records, rejects a malformed walk or NMI record,
  and otherwise calls the NMI policy exactly five times with the NMI count,
  the first four NMI records and the routing authority;
- calls the finish exactly six times with the last transition's status and
  error, the final state and the observation, exactly when the policy
  accepted;
- returns 0 exactly when the finish accepted, publishing its APIC ID,
  processor count and APIC base, and publishes no topology on any other
  status.

The law's Lean is the reference. It keeps its own copy of the state, the
answers and the record walk, and checks every call and the published result
against them. One law therefore gives both directions: each call is the one
the review requires, and each result is the one the answers decide.

Not claimed (`project/DEVIATIONS.md`):

- what the answers of the real Lean exports mean: the Lean theorems say that.
  The step that stays trusted is reading the law's protocol, the review table
  and the Lean statements as the same;
- that the span is the authoritative, envelope-validated MADT copy, or that
  the observation was read safely on the executing CPU: those are the
  caller's obligations;
- termination, though every loop is bounded;
- anything about the compiled kernel (CompCert's C is not GCC's).

## The proof's shape

`Defs.v` models the consumer as a state machine over the exports' answers:

- `run x (start x) h` is the consumer's stage after the answers `h`;
- `next_call x h` is the call it makes next;
- `consume x h` is its outcome when it returns.

The consumer's specification (`MadtSpecs.bind_pre_post`) is parameterized by
an abstract oracle `Ora gv x h`, the Lean behind the inputs `x` after it has
answered the calls `h`. Each export's specification asks it only for
`next_call x h` and records its answer. That is the strongest ordering fact
the consumer can promise, and the law's Lean needs it to discharge its own
checks. The postcondition says the Lean answered exactly the calls `h` of a
run with outcome `consume x h`, which the consumer published.

## Results

`qp verify` on a fresh clone: **PASS** ([`VERIFY.md`](VERIFY.md)).

| Theorem | Result | Axioms |
| --- | --- | --- |
| `consumer_obligations` | PROVED | 12: standard + VST malloc |

The statement and `whole_prog` are identical to the frozen contract, and the
regenerated Clight is identical to the committed Clight. The proof sources
contain no `Admitted`, `admit`, `Axiom`, `Parameter` or `Conjecture`.

`qp check` ([`CHECK.md`](CHECK.md)):

- 3,000 native ASan/UBSan runs and 20 CompCert-interpreter runs, all clean;
- 323 of 328 mutants killed. The five survivors change the size of a local
  array (`state`, `result`, `nmi`, `bound`) to a larger one, which the
  consumer never indexes past its first size, or the initializer of `result`,
  which every transition overwrites before the consumer reads it.

## Reproducing

```sh
scripts/check-quickproof.sh --check madt-consumer
```

[`check.conf`](check.conf) makes `qp check` run all 330 mutation sites
rather than a sample of 40, so the kill count the gate compares covers the
whole header. The env gives the interpreter no span of the maximal accepted
length: its 16 calls per byte take the CompCert interpreter minutes, past the
10 s per seed (1 of 20 seeds timed out), so there only the two lengths just
past the bound run, which the consumer rejects before any call. Native runs
keep all three.
`scripts/check-quickproof-pins.sh`, part of `scripts/check.sh`, fails when
`include/qotom_bsp_consumer.h`, `LeanOS/QotomMadtStream.lean` (the exports
the law's protocol and the shim's prototypes follow) or any file of
`project/` or `proof/` differs from [`pins.tsv`](pins.tsv).
